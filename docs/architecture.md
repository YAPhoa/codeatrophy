# Architecture

Codeatrophy is a single-user, self-hosted library for coding challenges and
technical readings. This document describes the components, the boundaries
between them, and the reasoning behind the main design decisions.

## Overview

```
                 ┌────────────────────────────────────────────┐
  browser ─────► │ web UI (embedded static files)             │
                 │ HTTP API    /api/v1   ─┐                   │
  MCP client ──► │ MCP server  /mcp      ─┤                   │
                 │                        ▼                   │
                 │  application services                      │
                 │   ├─ library   items, collections, tags    │
                 │   ├─ grader    submissions, verdicts       │──► judge engine
                 │   ├─ assist    drafting, test generation   │──► AI provider
                 │   └─ bundle    import / export             │
                 │  store (PostgreSQL or SQLite)              │
                 └────────────────────────────────────────────┘
                   codeatrophy server (Go, one binary)
```

The server is the only stateful component the project owns; its database is
PostgreSQL (the Compose default) or a SQLite file. The judge engine and the AI
provider are external dependencies reached through interfaces; the app
remains usable (as a library and reader) with either one absent.

There are two ways in — the HTTP API used by the web UI, and an MCP server
used by AI assistants — and both are thin adapters over the same application
services. Validation, defaults, side effects and concurrency checks live in
the services, so a change made through one transport behaves exactly like the
same change made through the other.

## Domain model

- **Item** — one entry in the library. `type` is `problem` (a coding challenge)
  or `reading` (a technical note or article). Both share a title, Markdown
  body, summary, tags, source attribution and personal state (status, favorite,
  notes). Problems additionally carry limits, starter code, saved solutions
  and test cases, and an *interface*: `program` (the solver writes a whole
  program) or `function` (the solver writes only a function or class, and a
  per-language *harness* turns it into a program; see
  [Solution-only problems](#solution-only-problems)).
- **Solution** — a saved program for a problem: another approach, another
  language, a brute force. At most one per problem is the *reference
  solution*, the one that computes and verifies expected outputs;
  `problem.referenceSolution` on the item is a view of it. A solution keeps
  the figures of its last run on the test cases (cases passed, slowest case,
  peak memory) until its code changes.
- **Test case** — stdin plus expected stdout for a problem. Sample cases are
  shown with the statement and used by "Run"; all cases are used by "Submit".
  Each case records its `origin` (`manual`, `ai`, `import`) and whether its
  expected output has been `verified` by executing the reference solution.
- **Collection** — a named, ordered list of items. Collections nest (a tree via
  `parentId`) and an item may belong to any number of them.
- **Tag** — a free-form label on items. A tag is recorded the first time an
  item carries it and stays, as an empty tag, when no item carries it any
  more, until it is deleted. Bundles carry only the tags of their items.
- **Submission** — one execution of user code against a problem, with a
  per-test-case result list and an overall verdict. For a function problem
  it keeps the harness it ran in and how many lines that harness put before
  the submitted code.
- **Working copy** — the code the user is writing on a problem, one per
  problem and language, kept on the server so that it follows them across
  browsers. Each write replaces it whole in one upsert (last write wins).
  It is personal work in progress, not content: writing it leaves
  `revision` and `updatedAt` alone, it goes with its item, and it is
  neither in bundles nor reachable over MCP.

Organisation is deliberately three independent axes: *collections* for curated,
ordered structure (a study plan, a topic tree), *tags* for cross-cutting
labels, and *personal state* (status, favorite, difficulty) for filtering.
Full-text search covers titles, bodies and tags.

All primary keys are UUIDs generated by the instance that created the record.
They are stable across export and import, which is what lets a re-imported
bundle update existing items instead of duplicating them.

## Server packages

| Package | Responsibility |
| --- | --- |
| `cmd/codeatrophy` | Entry point: configuration, wiring, subcommands |
| `internal/config` | Environment-based configuration |
| `internal/domain` | Core types and validation; no I/O |
| `internal/store` | Persistence interface and logical schema; `sqlite` and `postgres` implementations with their migrations; `dbcopy` (copying between stores), `dbopen` (choosing and opening the configured one); `storetest` (the conformance suite) |
| `internal/ai` | `Provider` interface, provider implementations, prompt and schema definitions |
| `internal/judge` | `Engine` interface and engine implementations |
| `internal/jobqueue` | `Queue` interface that schedules AI jobs, and its in-process implementation |
| `internal/grader` | Runs submissions through an engine, compares output, assigns verdicts |
| `internal/harness` | Assembles the program of a solution-only problem and maps line numbers in toolchain output back to the solver's code; no I/O |
| `internal/bundle` | Bundle reading, writing, validation and import planning |
| `internal/secrets` | Encryption of stored credentials (AES-256-GCM) and key management |
| `internal/app` | Application services: the transport-independent use cases built from the packages above |
| `internal/httpapi` | REST adapter: routing, handlers, request/response encoding |
| `internal/mcpserver` | MCP adapter: tool, prompt and resource definitions |
| `internal/webui` | Serves the embedded web UI with fallback to `index.html` for client-side routes |

Dependencies point inward: `httpapi` and `mcpserver` depend only on `app`,
which depends on `domain` and on the `store`, `ai.Provider` and `judge.Engine`
interfaces. Neither adapter contains business rules, and neither talks to the
store directly. Nothing outside `internal/judge/<engine>` or
`internal/ai/<provider>` knows which implementation is in use.

### Concurrent editing

A person in the web UI and an assistant connected over MCP can edit the same
item at the same time. Every item carries a `revision` counter that increases
on each content change. Writers may state the revision they based their edit
on; the service rejects the write with a conflict if the item has moved on.
The check is optional so simple clients keep working, but the UI and the MCP
tools both use it.

### Provenance

Every item records who created it and who made its last content change,
for tracking only. Each adapter puts a change source in the request's
context (`app.WithChangeSource`), and the services' write paths read it
wherever `updatedAt` moves, so both transports share one rule. `via` comes
from the transport: the HTTP adapter, the MCP adapter, or the bundle import
service. Over MCP, the client name from the initialize handshake and the
model a tool call reports are kept as the caller gave them, after
sanitising, and are not verified. For its own AI work the server knows the
model: an item saved from a draft records the model of the generation its
form was built from. No AI job writes to an item directly (their results
are reviewed and saved by a client), so jobs carry no change source. A
change with no source in its context, such as one made by a background
worker, is recorded as unknown. The record is local to the instance and is
not exported.

## Storage

The library lives in one of two databases behind the `store` interface:

- **PostgreSQL**, selected by `CODEATROPHY_DATABASE_URL`, is what the Compose
  stack runs: a database service of its own, on an internal network.
- **SQLite**, a single file in the data directory, is used when no URL is
  set: by a bare binary, by the tests, and by anyone who prefers one file to
  a database container. It stays fully supported.

Both are pure Go (`modernc.org/sqlite`, `pgx`), so the server still builds
into a static binary. All SQL lives in `internal/store/sqlite` and
`internal/store/postgres`; the services and both transports are the same for
either, and nothing outside `internal/store` knows which one is in use. The
data directory is needed with either, since it holds the secret key that
encrypts stored API keys.

**Same behaviour.** The application was written against SQLite, and the
PostgreSQL store reproduces what it relies on rather than asking the services
to change:

- *Writers are serialised.* SQLite allows one writer at a time, and the
  services' read-check-write sequences (revision checks, name uniqueness,
  limits, positions) depend on it. Every PostgreSQL write transaction
  therefore starts by taking one transaction-level advisory lock, so writes
  run one at a time and each sees everything committed before it; reads run
  in parallel on a repeatable-read snapshot, as SQLite readers do. This costs
  write concurrency, which a single-user library does not need.
- *Same values.* Ids, Unix-second timestamps, revisions and insertion order
  (`seq`) are stored as on SQLite. Text is ordered byte-wise (the `C`
  collation, like SQLite's `BINARY`; title sorting folds ASCII letters only,
  like `NOCASE`). Free text that has no control-character rule (bodies,
  sources, program input and output) is `bytea`, because PostgreSQL text
  cannot hold NUL and program output need not be valid UTF-8.
- *Same guards.* What SQLite enforces with constraints and triggers
  (immutable provider kind, at most 20 providers and 20 presets, 50 solutions
  per problem, one default preset, one reference solution, single-line
  names, case-insensitive unique names, length limits) PostgreSQL enforces
  with constraints and triggers too.
- *Same search.* SQLite uses FTS5 (`unicode61`, diacritics removed). The
  PostgreSQL store splits text with that same tokenizer, run on a private
  in-memory SQLite database, and stores each column as its token sequence; a
  query word is a phrase whose last token is a prefix, matched as a substring
  at a token boundary, and relevance is FTS5's bm25 computed in SQL with the
  same weights and statistics. Results and their order are the same; the
  PostgreSQL search scans the index table rather than using an inverted
  index, which is fine for a personal library (thousands of items) and would
  need an index for far larger ones.

`internal/store/storetest` is a conformance suite that both stores run, and
the application, HTTP and MCP tests run on either (`make test`,
`make test-postgres`).

### Links and deleted items

Items can be linked by hand: `item_links` holds one row per unordered pair
of item ids, the smaller id first, with the time it was made. Neither id
refers to `items`, and neither does `items.variant_of`: a link or a
variant's origin outlives the item it names. Deleting an item, by any path,
writes its id, title and type to `deleted_items`, so that the items that
still name it can show it as unavailable (a dead link, in the UI's red);
creating an item with that id again (an import brings it back, say) removes
the record, and the links come alive again. An import may also bring links
to items the library never had, which are unavailable without a title.
Links are not content: they leave `revision` and `updatedAt` alone, a bundle
carries them outside the content hash, and the rules (both items exist when
linked, at most `CODEATROPHY_MAX_LINKS_PER_ITEM` per item, 30 by default and
never more than the 50 a bundle item's `related` holds) live in the
application service that both transports call.

### Schema migrations

Each backend has its own embedded, numbered, forward-only migrations and a
`schema_migrations` record, and applies pending ones at startup, each in its
own transaction, logging each one. The numbers are *logical schema versions*
shared by both backends: PostgreSQL starts from one consolidated migration
(`0005_initial_schema.sql`) that yields the schema SQLite reaches with
0001–0005, including the built-in style presets seeded the same way (only
into an empty table, only once). Migration 0015 refreshes the text of each
built-in preset whose name and text are still exactly as seeded.

The rule for every later schema change: **add one migration per backend with
the same new number**, bump `store.SchemaVersion`, and update `store.Tables`
if tables or columns change. A test fails when the two backends' latest
versions differ or a number is missing on one side, and another when a
backend's tables differ from `store.Tables`.

SQLite cannot drop a constraint, so a change to one rebuilds the table. A
SQLite migration that rebuilds a table other tables refer to (as 0014 does
with `items`) starts with the line `-- foreign_keys=off`: the runner then
applies it with foreign key enforcement off, as SQLite's documented
procedure asks, so that dropping the old table deletes no rows that refer to
it, and commits only if `PRAGMA foreign_key_check` then finds every
reference intact.

- A database whose version is newer than the server knows is not opened:
  startup fails with "this database was last used by a newer Codeatrophy;
  upgrade the server", and nothing is written.
- Before migrating an existing SQLite database, the server writes a
  consistent copy next to it (`VACUUM INTO`), named after the version it was
  at (`codeatrophy.db.backup-v4-<timestamp>`), and keeps the three newest.
  PostgreSQL migrations hold an advisory lock for the whole step, so two
  servers starting together cannot both migrate; take a `pg_dump` before
  upgrading.
- `CODEATROPHY_DB_AUTO_MIGRATE=off` turns migrating at startup off: the
  server then opens only a database at its own version and otherwise stops,
  changing nothing, with both versions and the command to run. The automatic
  SQLite import (below) does not run in this mode either, since it migrates
  the SQLite file; with an empty PostgreSQL database and a SQLite file
  waiting, the server stops and points to `db copy`.
- `codeatrophy db status` and `codeatrophy db migrate` show and apply
  migrations without starting the server; `db migrate` lists the pending
  ones first, always migrates whatever the setting, and on PostgreSQL warns
  that no backup is taken.

### Moving between backends

`internal/store/dbcopy` copies the complete contents of one store into
another, in either direction, through the `store.Bulk` interface: every
table of the logical schema, rows in insertion order, values unchanged, then
the destination rebuilds its search index and sequences and checks foreign
keys. It runs in one transaction on the destination, which commits only when
every table has the same row count on both sides, and it refuses a
destination that already holds library data unless told to replace it.
"Holds no library data" means every table is empty except style presets, and
those are only built-in presets exactly as this version ships them, never
edited; any setting, provider, usage count, AI log entry, AI job, draft,
item, collection or submission counts. The destination's own seeded
presets are replaced by the source's. Stored API keys travel as ciphertext,
so the destination needs the same secret key.

The server uses it for an **automatic import**: when it opens PostgreSQL and
finds no library data there, and a SQLite file exists at
`CODEATROPHY_DB_PATH`, it migrates that file to the current version, copies
it in, checks the counts and renames the file (with its `-wal` and `-shm`) to
`<name>.migrated-<UTC timestamp>`, so it stays as a backup and is never
imported twice. A failure rolls everything back, leaves the file in place and
stops startup with what to do. If PostgreSQL already holds data, the file is
ignored with one log line. `CODEATROPHY_SQLITE_IMPORT=off` turns the import
off. This is how an existing Compose install moves to PostgreSQL on its first
start after the upgrade. `codeatrophy db copy` runs the same copy by hand,
including from PostgreSQL back to SQLite.

## Judge engines

The engine interface is intentionally narrow: *execute this source in this
language with this stdin under these limits and report what happened*.

```go
type Engine interface {
    Name() string
    Health(ctx context.Context) error
    Languages(ctx context.Context) ([]Language, error)
    Execute(ctx context.Context, req ExecRequest) (ExecResult, error)
}
```

Everything that makes it a *judge* — choosing which test cases to run,
comparing output, mapping results to verdicts, aggregating — lives in
`internal/grader`, not in the engine. This keeps an engine implementation down
to "a sandboxed runner", which is what makes replacing it realistic: a
home-grown engine only has to implement `Execute`.

Consequences of this split:

- Languages are identified by canonical ids (`python`, `cpp`, `go`, …) owned by
  the app. Each engine maps those to its own identifiers and reports which ones
  it supports.
- Output comparison is done by the app, so behaviour is identical across
  engines. Two modes exist: `tokens` (whitespace-insensitive, the default) and
  `exact` (trailing whitespace ignored).
- Engines may implement an optional batch interface as an optimisation; the
  grader falls back to bounded-concurrency single executions. Either way a
  batch streams each result as it finishes, the engine timeout applies to
  each chunk of work rather than to the whole set, and after the first engine
  error no further cases are started: the results that finished are kept and
  the rest are reported as `internal_error`, never re-executed.

The reference engine is [Judge0](https://github.com/judge0/judge0), run as
additional containers in the Compose stack and reached over its REST API. The
`none` engine disables execution; the UI then hides run/submit controls.

Judge0's sandbox (`isolate` 1.x) can only use control groups on hosts that
still provide cgroup v1. Most current distributions are cgroup v2 only, so the
adapter by default asks Judge0 for per-process time and memory limits, which
do not involve cgroups. The cost is that the memory limit becomes an
address-space limit, which is coarser and needs more headroom for runtimes
that reserve large virtual ranges. The adapter therefore adds a per-language
address-space allowance and, where the resident set is a fair measure (C,
C++, Rust, Python, Go, Ruby), enforces the problem's own limit on the peak
resident memory Judge0 reports. Java and Kotlin are submitted as Judge0
multi-file programs with explicit JVM flags (`-Xmx` set to the problem's
limit), because the JVM as Judge0 ships it needs several gigabytes of address
space. In this mode only the wall-clock limit stops a running program, so the
adapter keeps it close to the time limit. Operators on cgroup v1 hosts can
switch cgroup accounting back on. All of this stays inside the Judge0
adapter: the grader sees the same `ExecResult` statuses from every engine.

The adapter also asks Judge0 for an output-file limit large enough for the
largest expected output a test case may hold (`maxTestDataBytes`), and the
Compose stack raises Judge0's own ceiling to match; otherwise a correct
program printing more than Judge0's 1 MiB default would be cut off. When a
program is killed by a signal, the shell Judge0 runs it under appends a line
such as `Segmentation fault (core dumped)` to stderr; the adapter removes that
line only when it is provably the wrapper's (the exit code is 128 + that
signal and the line names the exact run command) and reports the signal in
the result's message instead, so the program's own stderr is kept intact.

Judge0 stores every submission it runs (source, input, expected and actual
output) in its own database and never removes one, while the app keeps its
own record and reads each result exactly once. The adapter therefore
deletes each submission in Judge0 (`DELETE /submissions/{token}`) once it
has read the result, single or batched. Judge0 allows that only with
`ENABLE_SUBMISSION_DELETE=true` and its authorization token (`AUTHZ_TOKEN`,
sent as `X-Auth-User`); with `AUTHZ_TOKEN` unset it refuses every delete. The
Compose stack enables deleting and gives both sides the same token, with a
default as for its passwords (`CODEATROPHY_JUDGE0_AUTHZ_TOKEN`); a server
run without a token leaves submissions in Judge0, and one whose Judge0
reports deletes disabled sends none. Deleting is best effort and off the
result path: tokens go into a bounded queue that one background goroutine
works through, so a failure never fails or delays a submission; it is
logged (the first as a warning) and the submission stays in Judge0. Judge0
refuses to delete a submission still queued or running, so a run the
adapter stopped waiting for (cancelled, timed out, a failed poll) is queued
as well and retried with backoff for about nine minutes until it has
finished. Left behind are only runs whose creation the adapter never saw
answered (no token), runs that never finish within those retries, tokens
dropped from a full queue, and whatever was queued when the server stopped.

Problems are judged on a stdin/stdout basis. That is the model every sandbox
supports natively and it keeps problems language-agnostic.

### Solution-only problems

A problem whose interface is `function` asks only for a function or class,
as interview sites do. Judging stays stdin/stdout: for each language the
problem carries a harness, a prefix and a suffix of hidden code, and the
program that runs is

```
prefix ⏎ submitted source ⏎ suffix
```

where ⏎ is a newline added only when the part before it does not already
end with one; nothing else is added or removed. The prefix defines what the
solution relies on (imports, helper types such as a list node), the suffix
reads one test case (one JSON value per line, one line per argument),
calls the solution and prints the result as JSON. The test cases themselves are
plain stdin/stdout, so the grader, the comparison and the engines are
unchanged.

- **One place builds every program.** Submissions, test-case verification,
  the verification step of test generation and the AI draft check all take
  their program from the same application function, which checks that the
  language has a harness (a `422` otherwise) and that the engine accepts the
  assembled program's size. Saved solutions, including the reference
  solution, hold only the solution part. A submission stores the harness it
  was created with, so a runner edited while it waits does not change what
  it runs.
- **Line numbers.** The solver's first line is line `lineOffset + 1` of the
  program, `lineOffset` being the prefix's line count. Compiler output and
  stderr are rewritten before anyone sees them (in the grader, for every
  execution): a location in the program's own file inside the solver's
  code gets the solver's line number; a location inside the runner gets
  its file name replaced by `<runner prefix>` or `<runner suffix>` and a
  line number relative to that part, so it is never mistaken for one of
  the solver's lines. The message formats were derived from real output of
  each toolchain Judge0 1.13 ships (CPython tracebacks; gcc, javac,
  kotlinc, rustc, mcs and tsc diagnostics, including gcc's and rustc's
  numbered source snippets; Go, Node.js, Ruby and JVM stack traces; C
  `assert`). Which file names count as the program's is the engine's
  knowledge, offered through the optional `judge.SourceNamer` interface;
  TypeScript runtime errors refer to the compiled JavaScript and are left
  alone, and Mono stack traces carry no line numbers. Anything not
  recognised is left as it is; `lineOffset` lets a client explain it.
- **Size.** An engine may report, through the optional `judge.SourceLimiter`
  interface, the largest program it accepts per language. Judge0 accepts
  single-file programs of any practical size (40 MB were tested), but
  extracts the files of a multi-file program — Java and Kotlin in
  per-process mode — only up to `MAX_EXTRACT_SIZE` (10 MiB by default,
  reported in `/config_info`); a larger file fails with a misleading
  "run: No such file or directory". Such a program is refused up front with
  a `422` that says why.

## AI providers

```go
type Provider interface {
    Name() string
    Model() string
    Generate(ctx context.Context, req GenerateRequest) (GenerateResponse, error)
}
```

`Generate` takes a system prompt, a user prompt and a JSON schema, and returns
JSON conforming to that schema. It also carries the provider's **effort
level** — `low`, `medium` or `high`, or none for the model's own default —
which each adapter maps to its own parameter: Anthropic's
`output_config.effort`, sent only where the Models API says the model takes
that level (a connection test asks for `low`), and `reasoning_effort` for
OpenAI-compatible endpoints and Gemini, sent on a connection test too so
that a server that does not take it fails there. With none, nothing is sent.

The two features built on it are provider independent:

- **Drafting.** The user supplies whatever they have — a pasted fragment, a
  half-remembered description. The model returns a complete, well-structured
  item (statement, I/O format, constraints, examples, difficulty, tags, starter
  code) *and a list of assumptions*: everything it inferred or invented to fill
  gaps. Nothing is saved until the user has reviewed the draft.
  For a problem the model also chooses the interface (`function` for an
  algorithmic problem whose heart is one routine, `program` when input and
  output are part of the task; the user may decide instead), writes the
  stubs and harnesses of a function problem, and writes a reference
  solution. A request may also give a test case count, and then the model
  adds hidden test cases after the examples, chosen by the same test-design
  guidance as test-case generation. The server then runs that solution on
  the draft's test cases — through the harness, with the judge's real
  toolchains — and reports per case whether it printed the stated output,
  so a wrong example or a runner that does not compile shows during review.
  This *draft check* runs code for something that is not saved, never fails
  the draft (no engine, an unreachable one, a compile error or a timeout are
  reported in it), runs every case (a draft has at most
  `CODEATROPHY_MAX_GENERATED_TEST_CASES`, 30 by default, besides large
  ones) and stops after 50 seconds or when the job is cancelled, and
  corrects nothing. For a function problem it then proves every harness, not only the reference solution's: each language's starter
  code, which is written to compile and run with a placeholder result, runs
  unchanged on the first example in the time the reference solution left
  (the languages in parallel), and any answer counts as a working runner.
  The same check runs on demand for a problem that is not saved yet (a
  draft after editing), on every test case and within five minutes, without
  an AI provider.
  The prompts tell the model which languages and versions the judge runs
  (Judge0 ships old toolchains: Python 3.8, Java 13, Go 1.13, ...), and the
  conventions require a Python harness prefix to start with
  `from __future__ import annotations`, without which hints such as
  `list[ListNode | None]` fail on Python 3.8. A model that forgets it gets
  it added to its draft's Python prefixes by the server; nothing else in
  model output is rewritten.
- **Test-case generation.** The model returns a reference solution (for a
  function problem only the solution part, written against the stub and
  harness it is shown) and a set of inputs with the outputs it predicts. Models are unreliable at computing
  outputs by hand, so when a judge engine is available the server executes the
  reference solution on every input and uses the *actual* output as the
  expected output, marking the case `verified`. Disagreements between predicted
  and actual output are surfaced to the user as a signal that the solution or
  the statement may be wrong. Without an engine, predicted outputs are kept and
  the cases stay unverified. The model is shown the problem's existing
  inputs (bounded, long ones cut) so that it adds to them, and a proposal
  whose input repeats an existing or earlier one (ignoring trailing
  whitespace) is dropped and counted; a draft's own repeated inputs are
  dropped too.
- **Large test cases.** Models write small inputs by hand, so on request a
  generation also asks for up to five *generators*: deterministic programs
  that read nothing and each print one input near the statement's bounds.
  They are asked to differ in the shape of what they print (the largest
  size, the worst case for the obvious slower approach, extreme values, a
  degenerate input), since each catches a different slow or wrong solution.
  The server runs each in the judge as a plain program (10 s, 512 MB),
  refuses an output over 1 MiB, empty, not UTF-8 or repeating an existing
  input or an earlier large case, then runs the reference solution on it
  under the problem's own limits for the expected output, and appends the
  results, in the model's order, as ordinary hidden test cases. The cases
  are independent and run in parallel, each its generator and then the
  reference solution, so several take about as long as one; one that fails
  never affects the others. In a draft this runs after the other cases and
  before the runners, inside the check's time bound and outside its case
  cap. Each case keeps its generator, which is stored with it when the
  case is saved: a stored generator marks a case as large. A client can
  also give a test case a generator instead of its stdin, which is how an
  MCP assistant adds large cases without pasting a megabyte into a tool
  call: the same step runs it and checks its output (shared by both paths),
  before the write transaction, and the request fails as a whole if one
  generator does. A new case given both its stdin and a generator (a
  draft's large case being saved) is stored as given without running it. The stdin is stored either way, so nothing has to run a
  generator again, and bundles carry it as a source file beside the input,
  outside the content hash.
  Large test data never enters a prompt (and so never the AI log): wherever
  a prompt lists test cases, one larger than 4 KiB is named with its size
  instead.
- **Variants.** From an existing item the model drafts a related new one — the
  same technique in a different setting, an easier or harder version, or a
  twist that breaks the original approach. A saved variant keeps a `variantOf`
  link to its origin, so families of related problems stay connected; the
  link stays, naming an unavailable item, if the origin is deleted. A
  variant keeps the original's interface unless asked otherwise, and gets
  the same reference solution and check as a draft.
- **Code generation.** For a problem as it stands in the editor, saved or
  not, the model writes the code of the languages the editor lists: a
  program problem's starter code, which reads the documented input inside
  the folded region and leaves the solving to the user, or a function
  problem's stubs and harnesses. The request carries the problem (title,
  statement, interface, samples), so it reads nothing from the library and
  works on unsaved edits; it uses the conventions and the style preset as a
  draft does, and only the languages asked for come back. For a function
  problem the server then proves each runner on the first sample as the
  draft check does. Nothing is saved; the code goes into the form.

### AI jobs

Every generation — draft, variant, test cases, code — runs as a **job** on
the server, not inside the HTTP request that asked for it. The service
validates the request as before (a bad field, AI switched off, an unusable
provider or style is refused at once, and no job exists), stores the job in
`ai_jobs` with the request body as sent, answers `202` with it, and hands
its id to a queue. A worker runs the generation with a context of its own,
derived from the server's and cancelled by `POST /ai/jobs/{id}/cancel`, so
navigating away or closing the browser changes nothing, and cancelling
aborts the provider call (the AI log records it as `cancelled`). When it
ends, one transaction stores the outcome — the exact body the old
synchronous endpoint answered with, or its error in the same shape — and
runs the completion step of the job's kind, if it has one.

```go
type Queue interface {
    Start(ctx context.Context, run Run)
    Push(id string)
    Cancel(id string)
    Stop()
}
```

The queue only schedules: what a job is and what state it is in live in the
database, which the service writes before telling the queue, and a worker
reads the stored status before it starts and again before it writes the
outcome, so a cancelled or deleted job is never overwritten. The one
implementation, `jobqueue.Local`, is a FIFO slice with a fixed pool of
`CODEATROPHY_AI_WORKERS` goroutines (default 2); nothing in it survives the
process. On start, jobs a previous process left `running` become `failed`
with code `interrupted`, and `queued` ones are queued again; on shutdown the
running ones are left as they are, for the next start to report. At most 20
jobs may be active. Finished jobs are kept for 3 days, and only while among
the newest 200; pruning runs when a job is inserted, at start and hourly.
Nothing assumes a job finishes while one request is open, so a queue that
hands work to a provider's batch API can replace `Local` without the
services or the API changing.

### Drafts

A **draft** is a new item in progress, kept in `drafts` until it is saved or
discarded; drafts never expire, are not part of bundles and are not reachable
over MCP. The client's review form is an opaque JSON document (`content`) the
server stores as given; the server owns the rest: the latest generation
request, the latest job, the latest `generation` (a `DraftResponse`) with a
counter `generationSeq`, the generation the form was last based on
(`basedOn`), whether the user has edited it, the last error, a revision and a
title. Starting a capture or a variant with AI creates a draft and its job
together; the job's completion step (kinds `draft` and `variant`) writes the
result into the draft and increments `generationSeq`, or sets the error, so
a draft is complete even when no browser was open. A job that is no longer
its draft's latest, or whose draft is gone, changes nothing. Revising and
retrying are new jobs on the same draft, one at a time. The state the UI
shows (`drafting`, `failed`, `ready`, `edited`, `new`) is derived on read,
never stored. Autosaves carry the revision they were based on and are
refused with a conflict when the draft has moved on. Saving runs the
ordinary item creation and deletes the draft in the same transaction;
discarding deletes it and cancels its job. An instance keeps at most 500
drafts.

### Accounting for AI requests

Every request the server sends to a provider — draft, variant, test
generation, code generation, and the generation step of a connection test of
a saved or environment provider — goes through one application function. When the
request ends (answered, failed, cancelled, or answered with something the
server cannot use) it writes, in one transaction:

- the provider's **usage counts**, a roll-up per provider id and UTC day in
  `ai_usage` (requests, failed, input tokens including cache reads and
  writes, output tokens, last use) updated by an atomic upsert, so the
  30-day window is a range sum and concurrent requests add up. The counts
  belong to the provider entry: they go when it is deleted.
- an entry in the **AI activity log**, kept in the database with every
  other record: the index row in `ai_log` (operation, item and title,
  provider, model, status, duration, the token breakdown), the request and
  response gzip-compressed in `ai_log_bodies`, and each distinct system
  text once in `ai_log_texts`. The log is append-only and keeps every
  request with its content until the user clears or prunes it; it outlives
  providers and items, is paged by number or by a keyset cursor over
  (created time, id), and is not part of bundles or MCP. What it stores of a request is built
  from the server's own provider-neutral request, never from the HTTP call,
  so no key or header can get in; request and response are each cut at
  256 KiB.

The write is bounded (five seconds) and never fails the request: a failed
write is logged and the response's `usage.logId` is `null`. The server's own
log gets one line per request with the operation and figures, never the
content. Token counts are what the service reports, and stay `null` where it
reports none: Anthropic reports input, output (including thinking), the
thinking part, cache reads and cache writes; an OpenAI-compatible service
reports input (from which its cached part is taken out and shown as cache
reads), output and, where it says so, the reasoning part, but no cache
writes. A retry inside an adapter (the Anthropic fallback retry) is one
request, with the figures of the call that answered.

Output is constrained at two levels. The JSON schema fixes the *structure* of
a response and is not negotiable, because the app has to parse and store it.
The system prompt carries the *authoring conventions* for the prose inside
that structure — section order, how formats and constraints are written, the
stdin/stdout convention. Users can add their own standing instructions as
named **style presets**, mark one as the default, and choose one each time
they draft, revise or create a variant. The chosen preset is appended to the
conventions; it can shape layout and tone but cannot override the
schema or the rules judging depends on.

The conventions themselves come in two kinds of part (`internal/ai/conventions.go`).
The *editable* parts are about the prose: statement sections, readings,
titles, tags, what makes a good test set. The *fixed* parts are what the app
depends on: stdin/stdout judging, the two interfaces and the harness
protocol, the folded input region, comparison, limits, language ids and
versions, expected outputs from a reference solution, the one HTML
block that renders (`<details>`) and code blocks marked as language tabs.
A user may replace
all the editable parts with one text of their own, a **custom system
prompt**, kept as an instance setting. A prompt then carries that text,
then the fixed parts gathered under their own heading, then the style
preset; without one it carries the built-in conventions with the two kinds
interleaved, unchanged, which a golden test pins. The rules each request
adds (drafting or variant rules, large test cases, the JSON-only answer)
and the schema are never editable. Test generation uses no conventions:
it has rules of its own (`internal/ai/testcaserules.go`), split the same
way. Their editable part, the test-design guidance (the reference solution
and how inputs are chosen and covered), may be replaced by a separate
**custom test case prompt**; the fixed part keeps the harness contract, the
judge's versions, the input-size cap, predicted outputs, samples, the Java
and Kotlin entry points, large test cases and the JSON-only answer, and
restates any such rule the editable wording carried. Without a custom text
the test-generation prompt is unchanged, which the same golden test pins.

### Prompt-injection posture

Generation mixes instructions with text the user did not necessarily write: a
pasted snippet, or the body of an item that arrived in someone else's bundle.
The design limits what such text can achieve rather than trying to detect it:

- **The model has no tools and no authority.** A generation call returns one
  JSON document. It cannot read the library, call the judge, or reach the
  network, so there is nothing for injected text to steer it into doing.
- **Nothing is saved without review.** Every generated draft, variant,
  test-case proposal and piece of generated code is shown to the user first.
- **Output is schema-checked** server-side before it is returned.
- **Untrusted text is passed as data**, in delimited blocks in the user turn,
  never concatenated into the system prompt. That includes stubs and
  harnesses taken from the library, and the language versions the judge
  engine reports (cut to one short line each).
- **Block delimiters cannot be forged.** Every data block (and the style
  preset block) is wrapped in tags carrying a random nonce chosen per prompt,
  such as `<user_input-3f9c…>`, and the nonce is guaranteed not to occur in
  any of the prompt's untrusted texts, so no text can close its own block or
  open another. The system prompt tells the model that only tags with this
  request's nonce delimit data. Tag-like text inside a block is also defanged.
  MCP prompts and the authoring guide use the same scheme.
- **The user-controlled slots in the system prompt are bounded and local.**
  Style presets have hard, non-configurable caps on length and count, reject
  control characters (and any line break in a name), and can only be created
  through the instance's own settings — never by importing a bundle and never
  over MCP. The one exception is the three built-in presets a new instance
  starts with: they ship with the app (seeded once, by a database migration,
  into an empty preset list) and are then ordinary presets the user can edit
  or delete; a later migration may refresh the text of one whose name and
  text are still as shipped. The custom system prompt and the custom test
  case prompt are each one text with the same character rules and a cap of
  20000 code points, set the same way only; tag-like
  text in it is defanged, the envelope's nonce avoids it like any other
  untrusted text, and the fixed rules that follow it say they win. Shared
  content therefore cannot plant standing instructions.
  Per-request instructions are length-capped as well.

A default preset, rather than "last used", decides what applies when a caller
does not choose: it is predictable, and it gives MCP clients and scripts —
which have no notion of a previous choice — the same behaviour as the UI.

Provider kinds: Anthropic, Google Gemini, and any OpenAI-compatible
endpoint, which covers most hosted services and locally run models. The
Gemini kind generates through Google's OpenAI-compatible endpoint
(`{base}/openai`, by delegating to the OpenAI-compatible implementation) but
lists models with Google's native Models API (`{base}/models`, the key in the
`x-goog-api-key` header): that API reports each model's supported generation
methods, so the list keeps only models that support `generateContent` and
leaves out embedding, speech, image and similar models without a hand-kept
list. Ids lose their `models/` prefix, which the OpenAI-compatible endpoint
does not take. The user saves any number of
named providers (up to 20), each with its own kind, key, base URL and model,
and chooses one as the default that the AI endpoints use; a provider stands
on its own values plus its kind's defaults. Environment variables add one
read-only provider per kind for unattended setups, and
`CODEATROPHY_AI_PROVIDER` makes one of them the initial default until a
default is saved. Providers are local configuration: they are never part of
a bundle and are not reachable over MCP.

Implementations may also satisfy an optional `ModelLister` interface, which
the connection test and the model listing (which makes no generation
request) use to show the service's models, so a model can be picked from a
list instead of typed. The list is bounded (time, response
size, entry count) and treated as untrusted text: ids that are not a short
single line are dropped before they reach the UI.

Stored API keys are encrypted (AES-256-GCM) with a key that is kept outside
the database: taken from an environment variable if set, otherwise generated
on first start into a file in the data directory. A database copy on its own
therefore does not expose provider credentials. Keys are write-only through
the API — responses carry only a "set" flag and the last four characters — and
are never exposed over MCP, written to logs, or included in bundles.

A key is only ever sent to the origin it was stored for. A saved key is
stored with the origin (scheme, host, port) of its provider's base URL at the
time, and the provider kind and that origin are bound into the ciphertext as
AEAD additional data, so a key cannot be decrypted for another origin even by
editing the database. Changing a provider's base URL to another origin
without entering a new key deletes its saved key; an environment key belongs
to the environment's (or default) base URL; and a connection test or model listing
against another origin sends only a key given in that request. Without this, anyone able to change the settings —
including a page that got past the request checks — could redirect the
stored key to a server of their choosing. For the same reason providers do
not follow a redirect to another origin: Go forwards custom headers such as
`X-Api-Key` on redirects, so the key would go with it.

Providers connect through one HTTP client (`ai.NewHTTPClient`) with an
egress policy, because a base URL is chosen by whoever can edit the
settings and the connection test shows part of the answer, which would
otherwise let the server be used to fetch from addresses only it can reach
(server-side request forgery). The policy is checked on the address actually
dialled, after DNS resolution, so a name cannot be re-pointed between a
check and the connection. Cloud metadata addresses (`169.254.169.254`,
`fd00:ec2::254`, `100.100.100.200`) and link-local ranges are always refused;
loopback and private ranges are allowed by default, since a local model
server is the common self-hosted case, and refused with
`CODEATROPHY_AI_BLOCK_PRIVATE`. `CODEATROPHY_AI_ALLOWED_HOSTS` lists host
names (matched against the URL as written), addresses and CIDR prefixes
that are exempt. Behind an HTTP proxy the proxy resolves names, so only base
URLs given as IP addresses can be checked there.

AI features can be switched off in the AI settings without forgetting the
default provider. While they are, or with no default provider chosen, or one
that is not ready, the AI endpoints return `ai_unavailable` and the UI falls
back to manual authoring.

## MCP server

The server exposes a [Model Context Protocol](https://modelcontextprotocol.io)
endpoint at `/mcp` (Streamable HTTP) so an AI assistant can read and edit the
library directly. `docs/mcp.md` lists the tools.

Design points:

- **Same services, no second code path.** Each tool is a thin wrapper over an
  application service that the REST API also uses.
- **The connected assistant is the model.** Over MCP the drafting and
  test-writing intelligence comes from the client, so these tools work with no
  AI provider configured on the server. The server contributes what a model
  cannot do itself: persistence, search, and *execution* — running a reference
  solution to compute and verify expected outputs.
- **Shared authoring guidance.** The conventions the built-in drafting prompts
  enforce (statement structure, stdin/stdout format, what makes a good test
  set) are published to MCP clients as the `get_authoring_guide` tool, a
  resource and prompts, so an
  item written by a connected assistant looks like one drafted in the UI. The
  user's style presets are readable over MCP, and the default one is part of
  that guidance, but presets cannot be changed from there. A custom system
  prompt replaces the editable conventions in that guidance too; no tool
  reads or sets it. A custom test case prompt is for the app's own test
  generation and is not part of the guidance.
- **Built for incremental edits.** Tools return compact results, support
  partial updates and targeted text replacement inside long Markdown bodies,
  and carry the item `revision` so an assistant never silently overwrites a
  concurrent human edit. Test data larger than 2 KiB in a tool result (16
  KiB on request) is replaced by its size and first bytes (in the MCP
  adapter only), so one large test case cannot fill the assistant's context.
- **The user's preferences.** `get_overview` reports the user's test case
  preferences and the test case limits, and the prompts follow them (how
  many cases, whether to add large ones as generators); like style presets,
  they cannot be changed over MCP.
- **Access.** The endpoint can be disabled, and can require a bearer token.
  It shares the HTTP API's request checks (below). Idle sessions are closed
  after 30 minutes and the number of open sessions is capped.

## Bundles

Import and export use a documented, versioned archive format
(`docs/bundle-format.md`): a zip of plain JSON, Markdown and source files, laid
out so that it is readable, diffable and hand-editable, and can live unzipped
in a git repository.

- Bundles carry *content* only — never personal state (status, notes,
  favorites, submissions, the last runs of solutions) or raw AI input. They are safe to share by default.
- The format is versioned. Version 2 adds solution-only problems (interface
  and harness); a bundle is written in version 1 unless it holds such a
  problem, so older servers keep importing everything they can represent
  and refuse, by version, what they cannot. Readers accept both versions.
- Items and collections keep their ids, so importing is idempotent. A preview
  step reports what an import would create, update or leave alone before
  anything is written, and the user picks a conflict strategy.
- Export scope is the whole library, a collection subtree, or an explicit
  selection of items.

## Web UI

A single-page app (React, TypeScript, Vite) compiled to static files and
embedded in the server binary, so the deployed artefact is one container.
It talks to the server only through `/api/v1`. In development the Vite dev
server proxies API calls to a running server, or serves an in-memory mock of
the API so UI work does not require the backend.

Item text is rendered as untrusted Markdown: GitHub-flavoured, with KaTeX
math and highlighted code, but no raw HTML, no unsafe URLs and no remote image
until the reader asks for it. Images embedded as `data:image/` URLs are shown
as images, where an SVG cannot run script. A ```` ```mermaid ```` block is
drawn as a diagram by Mermaid, loaded only when a page has one, at its
`strict` security level and in the app's theme; one that does not draw shows
its source with a short note. The one piece of HTML that renders is a
collapsible block: `<details>` (or `<details open>`), an optional
`<summary>…</summary>` and `</details>` around Markdown become a real details
element, rebuilt from those tags alone; the summary is plain text, and a tag
with any other attribute, or without its partner, stays text like other HTML.
Fenced code blocks marked `tab` after their language (```` ```cpp tab ````),
two or more one right after another, are drawn as one block with a tab per
language. The language picked in one group is picked in every group on the
page that has it, and remembered in the browser.

## Deployment

`compose.yaml` defines the server, its PostgreSQL database and the judge
engine's containers. The database is on an internal network shared only with
the server and is not published to the host. The server's port is published
on loopback only by default: the app can execute code, so exposing it beyond
the host is an explicit operator decision.

### Sign-in

The web UI and the HTTP API require a signed-in session unless the operator
sets `CODEATROPHY_AUTH=off`. Accounts (`users`) hold an email and a bcrypt
password hash. Accounts share one library and keep their own personal data
(below). The rules live in the application services
(`internal/app/auth.go`): validation, creating the first account,
sign-in with a per-address limit on failures, sessions, password
changes. The HTTP adapter maps them onto a cookie and gates `/api/` in front
of the routes; the `codeatrophy user` command uses the same services.

- **First account.** While no account exists, `POST /auth/setup` creates
  one with an email and password; once any exists it is refused. Whoever
  reaches the server first can claim it, which the operator closes by
  creating the account right after the first start (or with
  `codeatrophy user add`); the server logs a warning on each start until
  then.
- **Sessions.** A session is 32 random bytes, sent as an `HttpOnly`,
  `SameSite=Strict` cookie; the store keeps only its SHA-256 hash
  (`sessions`), so a database leak yields no usable cookie. A session lasts
  `CODEATROPHY_SESSION_TTL` from its last use; the expiry is pushed back at
  most once an hour per session, to keep reads from writing.
- **CSRF.** With a cookie the browser authenticates on its own, so
  state-changing requests also pass Go's `http.CrossOriginProtection`
  (`Sec-Fetch-Site`, else `Origin` against `Host`). Unlike the host-based
  origin check below, it tells apart another port of the same host.
- **MCP.** MCP clients cannot sign in with a password, so while sign-in is
  on `/mcp` requires a bearer token and is never the one open door. Each
  account makes its own tokens (`mcp_tokens`, stored as SHA-256 hashes like
  sessions, revoked with the account), and `CODEATROPHY_MCP_TOKEN` adds a
  server-wide one. The MCP adapter asks the services whose token it is, and
  hands the account to the SDK as the token's user, so each request acts for
  it and a session cannot be taken over with another account's token.

#### Personal data

The library (items and their content, test cases, solutions, tags, AI
providers, style presets) is shared. An item's status, favorite and notes,
collections, working copies, submissions, drafts, AI jobs, the AI log and
preferences belong to an account:

- **Which account.** The adapters put the account a request acts for in its
  context (`app.WithAccount`): the session's account, an MCP token's
  account, or with sign-in off (and for `CODEATROPHY_MCP_TOKEN`) the oldest
  account (`App.DefaultAccount`). Background work acts for the account that
  started it: a submission's verdict sets its submitter's status, and an AI
  job's requests are logged for its owner.
- **Item state.** `item_states` holds a row per account and item whose state
  differs from the default (todo, not a favorite, no notes). The stores join
  the context's account into every item read, filter and count, and item
  writes store its state for that account, so the services read and write
  items as before. Personal state never moves an item's `revision` or
  `updatedAt`, as it never did.
- **Other records** carry a `user_id`, which the services set and check:
  lists take the account, and a record of another account read by id is
  not found. Preferences are the setting `preferences:<user id>`.
- **Collections** carry a `user_id` too, and the stores scope every
  collection read and write, an item's `collectionIds` and the collection
  filters and counts to the context's account. Their ids stay unique on the
  server, so an import that brings a collection another account already
  has gives it an id derived from the account and the bundle's id
  (`accountCollectionID`), which a second import of the bundle finds.
- **No account yet.** The account `''` (`store.Unowned`) holds what is kept
  while no account exists, as with sign-in off from the start. The first
  account created takes it over in the same transaction, and migrations 20
  and 21 gave existing data to the oldest account. Deleting an account deletes its
  personal data.

The UI's static files stay public; `GET /api/v1/auth/session` tells the UI
whether to show the sign-in page. `GET /api/v1/health` needs no session, for
the container health check.

### Request checks

Two further request checks protect `/api/` and `/mcp` from web pages the
user happens to visit, with sign-in on or off:

- **Host allow-list (DNS rebinding).** A page on `attacker.example` can have
  its DNS name re-pointed at `127.0.0.1`; the browser then treats requests to
  the local server as same-origin and sends no foreign `Origin` header, so an
  origin check alone cannot stop it. What the browser does send is
  `Host: attacker.example`. The server therefore accepts only `Host` values
  that name it — loopback names and addresses, the host of the public URL,
  the hosts of the allowed origins, and `CODEATROPHY_ALLOWED_HOSTS` — and
  checks this before anything else. Reaching the server over the LAN by
  address or name requires listing it (or setting the public URL).
- **Origin check (CSRF).** State-changing requests that carry an `Origin`
  header must come from a loopback origin or the configured allowed origins
  and hosts. The comparison is against configuration only, never against the
  request's `Host`, which the attacker controls in the rebinding case.

The container's health check calls `GET /api/v1/health` on loopback with a
loopback `Host`, so it passes whatever the allow-list holds and needs no
session.

Configuration is by environment variable, documented in `.env.example`.

## Out of scope for the first version

- Separate libraries per user, roles, and single sign-on (OAuth, OIDC).
- Custom checkers and interactive problems.
- File attachments. The bundle format reserves an `assets/` directory per item.
